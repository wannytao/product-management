# Verify release artifacts with pinned signatures

V1 will distribute a signed release manifest covering the Compose definitions, operator scripts, OCI image digests, and artifact checksums for each application release and Recovery Kit. Update, installation, and recovery tooling will verify that manifest with a trusted public key pinned in the installed distribution and fail closed when the signature, digest, or declared artifact set is invalid. This provides offline verification independent of GitHub availability or account integrity; same-channel checksums, HTTPS transport, and GitHub attestations alone are not the release-authenticity boundary.

V1 will use one long-lived offline signing key as both the pinned trust anchor and the key that manually signs release manifests. It will not introduce an offline root with delegated release keys or place a long-lived signing secret in CI. This deliberately reduces release-operation complexity for the personal V1, while accepting that each signing use exposes the sole trust key and that compromise or unplanned loss makes rotation substantially harder.

The private signing key will be an encrypted key file with two offline copies held in separate physical locations; its passphrase will be retained separately from both media copies. Release signing will occur only in a network-disconnected signing environment that receives the unsigned manifest and returns the signed manifest, never on the development host or in CI. Each copy and a test signature will be verified periodically so redundancy is demonstrated rather than assumed.

Planned key rotation will use a transition release signed by both the previously trusted key and the proposed new key, with the new fingerprint shown for explicit operator review before trust changes. Suspected compromise or unplanned key loss cannot use that online trust path: update trust will remain blocked until the Workspace Owner supplies a replacement public key from independently verified media through the authenticated Operations interface, completes password step-up authentication, reviews the old and new fingerprints, records a reason, and explicitly confirms the reset. Both rotation and emergency reset create Administrative Audit Events; V1 will never bootstrap a replacement trust key solely from GitHub or a signature by the key under suspicion. Choosing a web reset deliberately accepts greater application attack surface than a host-only CLI procedure.

The Emergency Trust Reset route will be served only to a loopback browser connection on the application host and will remain unavailable through the private-network, VPN, or trusted-reverse-proxy access profile. Loopback access supplements rather than replaces the password step-up, independently sourced key, exact fingerprint review, reason, explicit confirmation, and audit requirements. V1 will not expose a setting that enables remote trust reset.

After an Emergency Trust Reset, the currently installed release may continue running, but every downloaded or cached artifact trusted only by the retired key is quarantined and cannot be installed. Recovery Kits signed only by that key become `Legacy trust — review required` and are ineligible for an automated recovery cutover until their contents are checked against a known-good offline source and a replacement manifest is signed with the new key. V1 will not use claimed pre-compromise timestamps to preserve trust or retain the old key as an alternate trust anchor.
