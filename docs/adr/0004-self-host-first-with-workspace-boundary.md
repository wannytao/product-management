# Self-host first with a Workspace boundary

The first release will be a self-hosted application for one person's use, avoiding the cost of public SaaS concerns such as billing, invitations, and organization switching. Every product-planning record will nevertheless belong to a Workspace from the start so that future collaboration and multi-organization isolation can be introduced without first untangling globally owned data; the V1 interface will not expose unnecessary multi-tenant complexity.

The supported V1 installation path will be a versioned Docker Compose bundle containing the application and PostgreSQL, with persistent database storage and loopback-only application binding by default. The bundle will provide explicit setup, backup, restore, and upgrade commands and documentation; it will not run schema upgrades or database backups merely because the containers start. Native Windows installation, an externally managed PostgreSQL database, and installation directly from source are outside the supported V1 path.

The only host environment covered by the V1 support claim will be a vendor-supported Windows 11 x64 release using Docker Desktop with its WSL2 backend and Docker Compose. Other Docker hosts may happen to run the bundle but will be treated as unsupported rather than implied members of an untested portability matrix. Expansion to organizational use must separately review Docker Desktop licensing, managed-device policy, and whether a Linux deployment baseline should replace or join the personal Windows path.

PostgreSQL data will persist in a Docker named volume. Supported backups will use the bundled PostgreSQL-aware command to write a `pg_dump` artifact outside that volume, and restores will populate a newly created volume before application validation. Copying live database files, bind-mounting the PostgreSQL data directory onto the Windows filesystem, and selecting alternative storage layouts during V1 setup are outside the supported recovery model.

The supported scheduled-backup path will be a bundled PowerShell script invoked by Windows Task Scheduler rather than a scheduler inside the application or Docker stack. Each run will create a PostgreSQL custom-format dump outside the named volume, generate a checksum, apply the seven-daily and four-weekly retention policy, and publish a narrowly scoped success or failure status that the Operations page can read. Task registration and choice of the encrypted off-host destination remain explicit operator actions; manual-only backup and untested third-party scheduling are not the V1 baseline.

The off-host backup artifact will be encrypted to an `age`-compatible public-key recipient as it is produced, without writing a plaintext staging dump. The application host and scheduled task require only the public recipient and will never retain the private recovery key. The checksum will cover the encrypted artifact, which can be restored on a replacement host only when the operator supplies the separately held private key. Destination-managed encryption, a password embedded for unattended backup, and machine-bound DPAPI encryption are not the supported baseline.

Backup readiness requires two separately located offline copies of the private recovery key and a successful encryption-and-decryption test before scheduled protection is treated as operational. The installation records only the public-key fingerprint and the owner's readiness acknowledgement, never the private key or a recoverable representation of it. Quarterly restore tests must exercise the real recovery key so that possession and usability are verified together; a single offline copy, host-resident custody, and inclusion in Workspace export are outside the supported recovery model.

A restore will always target a newly created Docker named volume while the current database volume remains untouched. With the application stopped, the recovery workflow will verify the encrypted-artifact checksum, decrypt and restore the PostgreSQL dump, apply only the compatible recovery path, and run schema plus application-level validation. The restored volume becomes active only after the Workspace Owner reviews the validation result and explicitly confirms cutover; validation success alone never triggers an automatic switch, and the previous volume is not automatically deleted.

After cutover, the previous database volume remains an identified rollback volume. It is eligible for deletion only after the recovered installation has operated for at least seven days and produced a successful post-cutover encrypted backup. The Operations page will continue to show the retained volume and its age; deletion requires fresh authentication, an explicit destructive-action review naming the exact volume, and a separate audited command. V1 never automatically deletes rollback volumes.

Quarterly recovery verification will restore an off-host backup with the real private recovery key into an isolated temporary stack and volume on the supported host. That stack will have no externally reachable network path and will never replace or write to the active installation. At least once per year, and whenever the recovery architecture materially changes, the operator will additionally rehearse the complete runbook on a separate compatible Windows host, including Docker bundle setup, restoration, application validation, and observed RTO. A checksum or decryption test alone is not a Restore Test Pass.

Every backup manifest will identify the exact application release and image digest, database schema version, and PostgreSQL major version that produced it. Recovery will first use that matching application and PostgreSQL release to restore and validate the database without applying application-schema upgrades. Only after the recovered version is proven usable may the operator create a fresh pre-upgrade backup and invoke the normal explicit upgrade workflow. Restoring an old backup directly into the latest application or combining recovery with migration is unsupported.

Each installed release will have an off-host Recovery Kit containing its Compose definitions, recovery scripts and runbook, manifest and checksums, and offline OCI image archives for the application and matching PostgreSQL release. The kit must be retained for as long as any retained backup references that release and exercised by recovery verification; it may be retired only after the final dependent backup expires. Registry availability and rebuilding old images from source are not recovery dependencies, and the kit contains neither deployment secrets nor the private recovery key.

Activating any restored database revokes every restored authenticated session before the application accepts traffic, preventing an expired or previously revoked token from reappearing with older database state. When the original installation pepper is unavailable, as in replacement-host disaster recovery, the operator must generate a new pepper and set a new Workspace Owner password through the local CLI recovery command before cutover. The pepper is never recovered from the database, Recovery Kit, Workspace export, or encrypted database backup.

Before cutover, the recovery workflow will present a Recovery Gap Summary containing the backup reference, successful backup-completion time, recovery start time, and maximum interval of changes that may be absent. It will state that the exact missing records cannot be determined when the former database state is unavailable. The Workspace Owner must explicitly acknowledge this potential loss before cutover, and the recovered installation will record that acknowledgement as an Administrative Audit Event; an in-RPO backup receives the same disclosure rather than an implication of zero data loss.

Backup and recovery will remain an operator responsibility in V1. Scheduled PostgreSQL backups, retention, off-host storage, and periodic restore verification will be managed outside the application. The application will provide a manual, versioned Workspace export for portability, but that export is not a substitute for a database backup; V1 will not include an internal backup scheduler or managed cloud-backup service.

The V1 operational baseline is one scheduled backup per day with an RPO of no more than 24 hours. Retention will include seven daily copies and four weekly copies, with at least one encrypted copy stored off-host. A restore test will be performed at least once per quarter so that backup success is not mistaken for recoverability.

After an outage is detected, the recovery-time objective is no more than four hours using a documented restore-and-redeploy runbook. V1 will not provide automatic failover, high availability, or 24/7 outage detection. Each quarterly restore test must exercise the runbook and confirm whether the four-hour target was met.

Application and database-schema upgrades will be explicit operator actions rather than a side effect of normal application startup. The upgrade command will run compatibility preflight checks, require a successful pre-upgrade database backup, and then apply versioned forward-only migrations. The new application version will start only after all migrations succeed; a failed or incompatible upgrade will be recovered through the backup-and-restore procedure rather than automatic down migrations.

A planned upgrade has a maintenance-window objective of no more than 30 minutes. The application will stop accepting reads and writes during migration and present an explicit maintenance state; V1 will not implement zero-downtime or mixed-version schema rollout.

The application will be private by default: the web process will bind to `127.0.0.1` unless the operator explicitly changes the deployment configuration. Access from another device must remain on a trusted private network or pass through a VPN and a TLS-terminating reverse proxy. PostgreSQL will not be exposed to an external network. Direct public-Internet exposure is outside the V1 operating model.

Workspace portability will use a full round-trip, versioned JSON package containing a manifest, schema version, and integrity checksum. It will include every Workspace-owned planning record, revision history, and published snapshot, while excluding passwords, authenticated sessions, application secrets, and deployment configuration. V1 import will be allowed only into an empty installation or empty Workspace: the complete package must validate before a single atomic import is committed, and merge import will not be supported.

Domain revision histories will carry Historical Actor references containing a stable actor key and display-name snapshot. Imported actors will remain non-authenticating historical identities rather than disabled accounts, while the receiving installation's Workspace Owner will be recorded for every post-import change.

Every published Workspace export schema version will remain importable by later application versions through a deterministic, forward-only migration chain with retained compatibility fixtures. Import will validate and migrate without modifying the source package, and an application will reject packages produced by a newer export schema that it does not understand rather than attempt a best-effort conversion.

Installation-scoped Administrative Audit Events will also be excluded from the Workspace portability package and cannot be imported. The owner may export them separately as read-only JSON or CSV evidence, and that operation will itself create an Administrative Audit Event.

An export package will be generated only after explicit authenticated confirmation and streamed directly to the requesting browser without retaining a server-side copy. The interface will warn that the plaintext package contains sensitive planning data and must be encrypted or stored securely by the operator. Application-managed export encryption and server-side export retention are outside V1.

Data-at-rest protection in V1 will rely on the host operating system: the deployment baseline requires full-volume encryption such as BitLocker or Windows Device Encryption, restricted host accounts, and a least-privilege PostgreSQL application role. Application secrets will live in protected deployment configuration outside source control. The application will not add field-level encryption because the application and its decryption key would share the same single host while search, indexing, export, and key recovery would become substantially more complex.

V1 observability will remain local and private. The application will emit structured local technical logs and expose a local health check, but it will send no usage, diagnostic, or error telemetry to an external service. Logs will redact planning content, passwords, tokens, and secrets, and will rotate with a 14-day retention period. Immutable domain history remains governed by the product rules and is not subject to technical-log rotation.

An authenticated, read-only Operations page will show the application and schema versions, database connectivity, the latest successful-backup timestamp reported by the external backup script, whether backup age exceeds the 24-hour RPO, and the date and result of the latest recorded restore test. This page provides visibility only: the application will neither schedule nor execute database backups.

When backup age exceeds the RPO or the quarterly restore test is overdue or failed, the application will display a Workspace-level System Health Warning in global navigation and link it to the Operations page. This operator warning remains separate from Product Attention Signals, does not block planning reads or writes, and disappears only when the reported operational condition returns to compliance.

Each external recovery exercise will be represented by an immutable Restore Test Record entered by the Workspace Owner. It will identify the backup tested and record the actor, start and completion times, observed recovery duration, Pass or Fail outcome, application-level validation checks, and notes. A successful `pg_restore` command alone is insufficient for Pass; a failed test will keep the System Health Warning active until a later test passes.

Restore Test Records will be retained immutably for the lifetime of the installation and cannot be deleted individually. They will remain outside the Workspace portability package but will be downloadable with Administrative Audit Events as a separate read-only Operations Evidence JSON or CSV export; creating that export will itself be audited.

Operations Evidence exports will reduce client-IP precision by default: IPv4 addresses will be represented at `/24` and IPv6 addresses at `/48`, while the permitted browser and operating-system context remains available. The Workspace Owner may deliberately request exact client IPs only after fresh step-up authentication and an explicit warning that the file contains sensitive source data. Selecting the exact-IP export will itself create an Administrative Audit Event.

The exact client IP will be retained as restricted source detail separate from the immutable Administrative Audit Event for no more than 90 days. After expiry it will be irreversibly deleted, while the event and its IPv4 `/24` or IPv6 `/48` network prefix remain for the installation lifetime. An exact-IP export can therefore include exact values only for events still inside that retention window; expiry never rewrites the underlying event.

Audit immutability in V1 is an application-level guarantee: supported application commands cannot edit or delete Administrative Audit Events, but the system will not claim resistance to an operator who directly controls the host or database. Operations Evidence exports will be versioned and carry a content checksum so later corruption or modification of the exported artifact can be detected. V1 will not add an event hash chain, installation signing key, or external append-only evidence service because none would provide the stronger claim without introducing key custody or an independent trust boundary.
